# Frontend guidelines and review checklist

This document is the reference a **senior frontend reviewer** would hold a pull
request against in `bllueprint-frontend`. It has two jobs:

1. Say how code is organised and written here (architecture, folders, component
   skeleton, styling, accessibility, testing, tooling).
2. Be the checklist that every change is reviewed against, including changes
   made by an AI assistant. The assistant must read §1 before touching code and
   must run §13 on its own diff before declaring work done.

Anything not covered here follows the Angular style guide and
`.github/copilot-instructions.md`. When the two disagree, this document wins
because it is more specific to this codebase.

---

## 1. How to use this document (the review loop)

Before writing code:

- Read §2 (architecture) and §4 (component skeleton). Decide **where** the
  code lives before deciding **what** it looks like.
- If the change touches styles, themes or fonts, also read
  `src/sketch-ui/README.md`.

After writing code, before reporting completion:

- Walk through §13 item by item against the actual diff (`git diff`), not from
  memory. Each item is either satisfied, deliberately violated with a reason, or
  fixed.
- Run the tooling gate (§12): lint, tests, build, Prettier and `npm audit`.
- If the change touches `index.html`, Electron, IPC, dependencies or rendered
  content, also walk through §10 (security).
- Report the result of the walk-through in the final message: what passed,
  what was consciously left out and why. "Follows best practices" without the
  walk-through is not an acceptable answer.

When the review finds a problem that is really a missing rule, add the rule
here in the same change.

## 2. Architecture

### 2.1 Folder map

```
src/
├─ main.ts                 bootstrap only (+ side-effect imports for Monaco)
├─ index.html              inline theme script (kept in sync with ThemeService)
├─ styles.scss             global reset for the legacy editor chrome ONLY
├─ electron.d.ts           ambient types for the Electron preload bridge
├─ app/
│  ├─ app.ts / app.config.ts / app.routes.ts
│  ├─ core/                app-wide, feature-agnostic building blocks
│  │  ├─ layout/           shell, sidebar (things that frame every page)
│  │  └─ monaco/           editor engine setup (language, themes, workers)
│  ├─ features/<name>/     one folder per functional area
│  │  ├─ pages/<page>/     routed or tab-hosted screens (smart components)
│  │  ├─ components/<c>/   components used only inside the feature
│  │  ├─ directives/       directives used only inside the feature
│  │  └─ services/         feature-scoped services (not providedIn root unless shared)
│  └─ state/<slice>/       cross-feature signal stores (+ models/, constants/)
└─ sketch-ui/              the design system (framework-level, app-agnostic)
   ├─ core/                ThemeService, SketchConfigService (alias @sketch-ui/core)
   ├─ elements/            in-house sketch directives/components (alias @sketch-ui/elements)
   ├─ components/          Spartan helms generated by the CLI — never edited by hand
   └─ styles/              tokens, themes, scoped reset, .sk-* classes
```

### 2.2 Dependency rules (the ones a reviewer checks first)

| From          | May import                                     | Must not import             |
| ------------- | ---------------------------------------------- | --------------------------- |
| `sketch-ui/*` | Angular, Spartan, other `sketch-ui`            | anything under `app/`       |
| `core/*`      | `sketch-ui`, `state`, Angular                  | `features/*`                |
| `state/*`     | its own models, Angular                        | components, `features/*`    |
| `features/A`  | `core`, `state`, `sketch-ui`, its own folder   | `features/B` (go via state) |
| `pages/*`     | everything above + its feature's `components/` | other features' components  |

A page is the only place that composes a screen. A component in
`features/<x>/components/` must be reusable inside that feature and must not
know about routing or workspace tabs.

### 2.3 Import paths

- Cross-folder imports use the aliases: `@app/core/...`, `@app/features/...`,
  `@app/state/...`, `@sketch-ui/<pkg>`. Relative paths are only for siblings
  (`./foo`, `../models/bar`). Three or more `../` in a row is a review finding.
- Aliases live in `tsconfig.json`. Changing them requires restarting `ng serve`.

### 2.4 State

- One signal store per slice, `@Injectable({ providedIn: 'root' })`, private
  writable signals exposed as `asReadonly()` plus `computed()` views.
- Stores own transitions. Components call intent methods (`openTab`,
  `closeTab`), never `set` from outside.
- Orchestration that touches more than one store lives in **one** place (a
  small facade service), not copied into every caller.
- Stores never touch the DOM, `localStorage` or `document` directly; persistence
  goes through a service with try/catch (storage can be unavailable in Electron
  and private windows).

## 3. TypeScript rules

- TypeScript only. No `.js` in `src/` (the `scripts/` folder is build tooling
  and is the only exception). `allowJs` stays off.
- `strict` plus the flags already in `tsconfig.json`
  (`noImplicitOverride`, `noPropertyAccessFromIndexSignature`,
  `noImplicitReturns`, `noFallthroughCasesInSwitch`). Never weaken them per file.
- No `any`. Use `unknown` and narrow. No non-null assertions (`!`) except on
  `viewChild.required` style APIs that already guarantee presence.
- Prefer `interface` for object shapes, `type` for unions and aliases.
  Exported types live next to their owner (`models/` for state, the component
  file for component-only types).
- Pure helpers (`makeRows`, `compareRows`) are module-level functions, not
  methods, so they are testable without a `TestBed`.
- `readonly` on every field that is not reassigned. Constants in
  `SCREAMING_SNAKE_CASE` at module level.
- No `console.log` left behind. `console.error` only in bootstrap or an error
  handler.
- Comments explain **why**, never what the next line obviously does. English only.

## 4. Component skeleton

Every new component, directive or service follows this shape. Deviations need
a comment saying why.

```ts
import { ChangeDetectionStrategy, Component, computed, inject, input, output } from '@angular/core';
import { SomeStore } from '@app/state/some/some.store';

/** One sentence: what this component is for and where it is used. */
@Component({
  selector: 'app-thing',               // `app-` for app code, `sk-` for sketch-ui elements
  imports: [/* only what the template uses */],
  changeDetection: ChangeDetectionStrategy.OnPush,
  templateUrl: './thing.html',          // inline `template:` when under ~15 lines
  styleUrl: './thing.scss',             // omit when there is no style
  host: {
    class: 'thing',                     // host bindings go here, not @HostBinding
    '(keydown.escape)': 'close()',      // host listeners go here, not @HostListener
  },
})
export class ThingComponent {
  // 1. injected dependencies (private unless the template needs them)
  private readonly store = inject(SomeStore);

  // 2. inputs / outputs / models (signal APIs, never decorators)
  readonly label = input.required<string>();
  readonly disabled = input(false);
  readonly selected = output<string>();

  // 3. local state (signals) and derived state (computed)
  protected readonly items = computed(() => this.store.items().filter(...));

  // 4. template-facing handlers (protected, verbs)
  protected select(id: string): void {
    this.selected.emit(id);
  }

  // 5. private helpers
}
```

Rules behind the skeleton:

- `changeDetection: OnPush` on **every** component. No exceptions.
- Do not write `standalone: true`; it is the default.
- `inject()` instead of constructor parameters. Constructors only register
  `effect()`s.
- `input()` / `input.required()` / `output()` / `model()` / `viewChild()` /
  `contentChild()`. The decorator forms (`@Input`, `@ViewChild`, `@HostListener`)
  are review findings.
- Do not import `CommonModule`. Native control flow (`@if`, `@for`, `@switch`)
  needs nothing; import `NgTemplateOutlet`, `AsyncPipe`, etc. individually.
- Template-facing members are `protected`. Public API of a component is only
  its inputs/outputs.
- Derived values are `computed()`, not methods called from the template. A
  method in a binding (`[attr.x]="fn(a)"`) is acceptable only when it depends on
  loop variables and is O(1).
- Lifecycle: prefer `afterNextRender` / `afterRenderEffect` and `DestroyRef`
  over `ngAfterViewInit` / `ngOnDestroy`. When a third-party library needs an
  element (Monaco), use `viewChild.required` + `afterNextRender`.
- DOM access is confined to directives or to a component that explicitly wraps
  a native/third-party element. A page component running `querySelectorAll`
  over its own template is a review finding; extract a directive.
- Keep files short: a component over ~150 lines of TS or a template over ~200
  lines should be split (the playground page is the known exception; it is a
  catalogue).
- Naming: `thing.ts` / `thing.html` / `thing.scss` / `thing.spec.ts` (no
  `.component` suffix, matching the Angular 20+ schematics used here). Class
  names keep the suffix: `ThingComponent`, `ThingDirective`, `ThingService`,
  `ThingStore`.

### 4.1 Directives

Same rules. Use directives for behaviour attached to native elements (close on
outside click, keyboard navigation, resize observers). Selector form
`[skThing]` for sketch-ui, `[appThing]` for app code.

### 4.2 Services

- Single responsibility, `providedIn: 'root'` only for genuine singletons.
- Side effects on the document (`classList`, custom properties) live in one
  service (`SketchConfigService`, `ThemeService`), not scattered in components.

## 5. Templates

- Native control flow only; `track` by a stable id, never by `$index` for
  data that can reorder.
- `[class.x]` / `[style.x]` bindings; no `ngClass` / `ngStyle`.
- No business logic in templates: no `.slice()`, `.filter()`, string building.
  Move it to a `computed()`.
- Every interactive thing is a `<button type="button">` or an `<a href>`. A
  `<div (click)>` is a review finding unless it also has `role`, `tabindex` and
  keyboard handlers (Enter **and** Space), and a comment saying why a button is
  not possible (e.g. nested interactive content).
- `aria-*` and `role` go on the element that the pattern requires (`aria-sort`
  on `<th>`, `aria-selected` on the tab, `aria-current="page"` on the active
  nav item).
- Icons are `aria-hidden="true"`; the text label carries the meaning. Icon-only
  buttons get `aria-label`.
- `title` is not an accessible name. Use `aria-label` or visible text.

## 6. Styling

- Read `src/sketch-ui/README.md` first. Hard rules that are also checked here:
  no literal colors outside `sketch-ui/styles/themes/` and the Monaco hex
  mirrors; accent usage (soft tint = active, light hatch = hover, solid =
  primary); text never on top of a hatch.
- Component SCSS holds **layout** of that component only (grid, flex, sizes).
  Anything reusable or themed goes to `sketch-ui/styles/*.css`. The
  per-component budget is 16 kB.
- BEM-style class names scoped by a block that matches the component
  (`.home`, `.home__option`, `.pg__toolbar`). No element selectors in component
  SCSS beyond `:host`.
- Pseudo-element tricks and negative margins to compensate another rule are a
  smell; fix the rule that caused it.
- Native form controls that need a wrapper for styling (range input) are
  wrapped by a sketch-ui element, so callers never have to remember the
  wrapper.
- Tailwind utilities are allowed inside the Spartan helms and `spartan-sketch.css`
  only. App templates use the `.sk-*` classes or component SCSS.

---

## 7. Accessibility

- Keyboard: every action reachable with Tab + Enter/Space; Escape closes
  overlays and menus; focus returns to the trigger.
- Focus visible: dashed accent outline (`--ring`) on every focusable element.
- Contrast: text at WCAG AA against the paper of every theme; verify in all
  themes (the playground has "All themes side by side").
- Menus built on `<details>` must close on outside click, Escape and item
  activation (see `skMenu`).
- Sortable tables: `<th aria-sort>` with a real `<button>` inside.

---

## 8. Performance

- `OnPush` + signals everywhere; no manual `ChangeDetectorRef` calls.
- Large lists: `track` by id; sorting/filtering in a `computed()` so it runs
  once per change, not once per check.
- No work in template-bound methods that allocates per call.
- Feature routes lazy-loaded (`loadComponent`) once there is more than one real
  route. Workspace tabs stay mounted on purpose (Monaco state); keep that
  documented where it happens.
- Clean up every subscription, observer and third-party instance with
  `DestroyRef.onDestroy`.

---

## 9. Testing

- Runner: Vitest through `ng test`. Spec files sit next to the unit:
  `thing.spec.ts`.
- Minimum: every store has a spec for its transitions; every pure helper has a
  spec; a component with logic (sorting, filtering, keyboard handling) has a
  spec that drives it through the DOM.
- Specs must stay green. A stale spec (asserting markup that no longer exists)
  is worse than no spec; delete or fix it in the same change that breaks it.
- Do not test Spartan helms or Monaco; test the glue around them.

End-to-end (Playwright, `playwright.config.ts`, folder `e2e/`):

- `npm run test:e2e` — project `web`: smoke + regression against the
  **production build** served by `e2e/serve.mjs` (same bundle and CSP as the
  desktop app). Runs in CI on every PR. Every user-facing behaviour change gets
  a case here (navigation, keyboard, menus, sorting, theme persistence) and
  every test asserts a clean console.
- `npm run test:e2e:visual` — project `visual`: one screenshot per theme.
  Baselines are per platform; generate them on the platform that runs them
  (CI = Linux) with `--update-snapshots` and commit them next to the spec.
- `npm run test:e2e:electron` — project `electron`: smoke test of the
  **packaged** app (`BLLUEPRINT_APP_EXE`), run by the release pipeline after
  `electron-builder`: `app://` scheme, CSP, sandboxed bridge, Monaco,
  permissions denied.
- Selectors: roles and accessible names first (`getByRole`, `getByLabel`),
  stable classes second; never nth-child chains on layout.

## 10. Security

The app runs inside Electron, so the renderer is one XSS away from the user's
machine. These rules are checked on every change that touches `index.html`,
`main.ts`, the Electron main/preload, dependencies or anything that renders
external content.

- **Content-Security-Policy**: defined once, as a `<meta>` in `src/index.html`,
  and it applies in the browser, under `ng serve` and under the `app://` scheme.
  Baseline: `default-src 'self'; script-src 'self'` (no inline scripts, no
  `unsafe-eval`), `style-src 'self' 'unsafe-inline'` (Angular and Monaco inject
  styles), `worker-src 'self' blob:` (Monaco worker shim), `object-src 'none'`,
  `base-uri 'self'`. Loosening any directive needs a comment in `index.html`
  and an entry in §14.
- **No inline scripts.** Bootstrap code that must run before Angular goes in
  `public/*.js` (see `public/theme-init.js`).
- **Electron `BrowserWindow`**: `contextIsolation: true`, `nodeIntegration: false`,
  `sandbox: true` (plus `app.enableSandbox()` globally), `webSecurity: true`,
  no `bypassCSP`, `setWindowOpenHandler` denies new windows, `will-navigate`
  blocks navigation away from the app and the default session denies every
  permission request (camera, microphone, geolocation, notifications). The
  preload exposes a minimal, explicitly typed API through `contextBridge` and
  must stay sandbox-compatible (no `require` of project files).
- **Packaged build check**: before a release, open the packaged app and confirm
  `bllueprint://app/` loads the editor and the playground with an empty console.
  The scratch script used on 2026-10-16 drove `Bllueprint.exe
--remote-debugging-port` over CDP; a Playwright `_electron` test should
  replace it (see §14, open items).
- **IPC**: every channel is a constant, handled with `ipcMain.handle`, validates
  its arguments and never passes paths or shell commands from the renderer
  through unchecked.
- **Rendering untrusted content**: never bind to `[innerHTML]`; the DSL text
  shown by Monaco is a model value, not markup. If HTML rendering is ever
  needed, sanitize with `DomSanitizer` and record the decision in §14.
- **Dependencies**: `npm audit --omit=dev --audit-level=high` must be clean
  (CI blocks on it); tooling advisories are reviewed weekly through
  Dependabot. New runtime dependencies need a one-line justification in the
  PR. Install with `--legacy-peer-deps` only when the npm 10.9 crash forces it.
- **Secrets**: none in the repo, none in the bundle. Config that differs per
  environment goes through the Electron main process, never into Angular
  source.
- **Storage**: `localStorage` holds UI preferences only (theme, fonts). No
  tokens, no user content.

## 11. Git and PR hygiene

- One concern per commit; message in English, imperative mood
  (`feat(playground): add header sorting to the datagrid`).
- A PR that changes behaviour includes: the why, a screenshot for visual
  changes (both themes when colors are involved), and the §13 walk-through.
- No generated artefacts (`dist/`, `.nx/`, `.angular/`) in commits.
- Documentation updated in the same PR (`README`, `sketch-ui/README.md`, this
  file).

## 12. Tooling gate

Run before declaring any change done:

```bash
npm run lint                                  # angular-eslint (TS + templates)
npx ng test --watch=false                     # vitest, must be green
npx ng build                                  # production build, budgets enforced
npx prettier --check src docs e2e playwright.config.ts eslint.config.js
npm audit --omit=dev --audit-level=high       # runtime dependencies must be clean
npm run test:e2e                              # web regression (builds first)
```

The same steps run in `.github/workflows/ci.yml` (jobs `frontend` and
`desktop`) on every pull request. Releases go through
`.github/workflows/release.yml`: verify → e2e-web → package per OS (with the
packaged smoke test and optional code signing from secrets) → draft GitHub
Release. Formatting is Prettier's job (`.prettierrc`); do not hand-format.

## 13. Review checklist (run against the diff)

Architecture

- [ ] Every new file is in the folder §2.1 prescribes, and the dependency
      table §2.2 holds (no `core → features`, no `sketch-ui → app`).
- [ ] No cross-folder relative import with three or more `../`.
- [ ] Multi-store orchestration lives in one place, not duplicated.

Components

- [ ] `OnPush` set; no `standalone: true`; no `CommonModule`.
- [ ] Signal APIs only (`input`, `output`, `model`, `viewChild`, `host`).
- [ ] Derived state is `computed`; no logic in templates.
- [ ] No `querySelector` in a page/component unless it wraps a native element.
- [ ] Lifecycle via `afterNextRender` / `DestroyRef`; cleanup present.
- [ ] Template-facing members `protected`; file under the size limits or split.

Templates and accessibility

- [ ] Interactive elements are buttons/links or have full keyboard support.
- [ ] `aria-*` on the right element; icons hidden; icon buttons labelled.
- [ ] Menus/overlays close on outside click and Escape.
- [ ] Verified in every theme (side by side) when colors or focus changed.

Styling

- [ ] No literal colors outside themes; tokens used; accent rules respected.
- [ ] Component SCSS is layout only, BEM, within budget.
- [ ] No compensating hacks (negative margins, `!important`).

TypeScript

- [ ] No `any`, no `!`, strict flags untouched, helpers are pure functions.
- [ ] No dead code: unused imports, fields, controls without effect.

Security

- [ ] No inline script; CSP in `index.html` unchanged or loosened with a
      comment and a §14 entry.
- [ ] No `[innerHTML]`, no `eval`-like APIs, no `bypassSecurityTrust*`.
- [ ] Electron `webPreferences` untouched (isolation, sandbox, webSecurity);
      new IPC channels validate their input.
- [ ] `npm audit --omit=dev --audit-level=high` clean; new runtime dependency
      justified.

Tests and tooling

- [ ] Specs added/updated; none stale. `npm run lint`, `ng test`, `ng build`,
      `prettier --check` and `npm audit --omit=dev` pass.
- [ ] User-facing behaviour changes have an e2e case; `npm run test:e2e` passes.
- [ ] Docs updated (`README`, `sketch-ui/README.md`, this file).

Report

- [ ] The final message lists each unchecked item with the reason.
